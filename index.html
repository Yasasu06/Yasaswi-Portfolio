01

IT Support RAG Agent

Live and fully functional

An AI assistant that answers IT support questions by retrieving and citing real enterprise incident tickets, with adaptive retry and confidence scoring.

IT support teams repeatedly resolve similar tickets without a fast way to search past resolutions. This tool lets someone describe an issue in plain language and get a grounded answer sourced directly from historical tickets — with citations, not a hallucinated guess — including a live connection to a real ServiceNow instance.

Stack

PythonStreamlitLangGraphChromaDBOpenAI GPT 4o miniOpenAI EmbeddingsMicrosoft PresidioServiceNow REST APIpytestGitHub ActionsRailway

Key features

  • A LangGraph pipeline with four agents: Retrieval Agent (ChromaDB semantic search) → Answer Agent (grounded generation, cites ticket IDs) → Verification Agent (independent LLM fact check) → Triage Agent (confidence and groundedness scoring, automatic escalation)
  • Adaptive retry: broadens and reruns the query (max 2 retries) when confidence is low — visible in the UI as a "Broadened search · N retries" badge
  • Live ServiceNow REST API integration alongside 4 other ingested data sources
  • PII masking via Presidio before any data reaches the LLM
  • Rate limiting scoped per session (15 requests every 60 seconds) and a feedback loop (Helpful or Not Helpful voting)

What I did

  • Diagnosed and resolved a live ServiceNow production outage from start to finish: isolated a 401 error via direct curl and Python REST tests, used ServiceNow's Background Script tool to inspect system properties, identified a newly enforced Basic Auth role restriction, and fixed it
  • Documented fine tuning as a closed architectural decision (not pursued further) after confirming OpenAI deprecated self serve fine tuning for new orgs — a deliberate scope decision, not a gap
  • Directed visual design iteration using Linear.app as a reference
  • Identified and specified the retry visibility feature, surfacing an existing backend capability that was invisible to end users

Cloud Intelligence Platform

Live and publicly accessible

A cloud cost analyzer that uses an LLM to parse real billing CSVs and return personalized waste recommendations in under 60 seconds.

Startups spending $2K–$50K/month on cloud have no cheap way to understand where money is going. AWS bills have 14+ line items across multiple services and no clear signal on what's waste. This tool does what a FinOps consultant would do manually — takes the actual bill, finds the specific waste, and tells you what to cut this week.

Worth noting

The original bill analyzer here was using hardcoded fake data despite claiming to run real analysis. I rebuilt the CSV parser from scratch so it could handle five real billing formats. Separately, I found the Groq API key exposed in the browser bundle and moved all nine Groq call sites behind a single secure backend proxy route.

Stack

Next.js 14TypeScriptTailwind CSSFramer MotionDM Serif DisplaySupabaseGroq API (Llama 3.3 70B)RechartsStripe (test mode)PostHogAWS Pricing APIAzure Pricing APIVercelGitHub Actions

Key features

  • Parses real billing CSVs from AWS, Azure, GCP, DigitalOcean, and Oracle — automatically detects the provider with a confidence score, and shows rows parsed, services found, and cost column detected
  • Groq AI generates personalized recommendations with specific dollar savings based on actual bill data — not industry averages
  • Bill history with memory — anonymous users get localStorage persistence, authenticated users get Supabase storage with month over month trend comparison
  • Compliance checker — pick industry and cloud provider, get instant framework requirements (HIPAA, SOC2, etc.) with specific services and cost estimates
  • Live pricing explorer — compares 12 providers in real time using AWS and Azure APIs plus verified static data for remaining providers

  • Wrote the full Supabase schema from scratch — 7 tables, RLS policies, handle_new_user trigger, anonymous to authenticated migration

03

Entity Resolution Pipeline (Walmart–Amazon)

In Progress

A blocking and matching system that identifies when product listings from two independent retailers describe the same real world item, without ever using labeled training data.

Retailers routinely hold multiple records for the same product across different data sources, with no shared ID and inconsistent formatting. Naively comparing every record pair is computationally infeasible at scale. This project narrows an infeasible comparison space down to a manageable candidate set with high recall, then scores those candidates on multiple pieces of evidence — all without access to ground truth labels during development.

Stack

PythonDuckDBSplinkGit / GitHubpytest

Dataset: "Dirty Walmart–Amazon" entity matching benchmark (Amazon: 22,074 records; Walmart: 2,554 records).

Key features

  • Custom blocking layer with five rules: rare token matching, identifier pattern detection, brand vocabulary harvesting, character n gram matching, and a symmetric nearest neighbor fallback. This reduced 56.4 million possible pairs down to about 564,000 candidates (a 99.1% reduction) while keeping 100% record coverage on both source tables
  • Evidence extraction across the full record text (rather than trusting original field structure, which is unreliable due to data corruption) — recovered usable identifier and brand evidence for 72–99% of records versus 16–25% using original fields directly
  • A custom word level title similarity comparison, built after verifying that Splink's built in "Jaccard" comparison operates on characters rather than words and isn't discriminative on product titles that run about 100 characters long
  • Strict data governance policy: no labeled data read at any point during design, tuning, or threshold setting, only at a single final evaluation. All required statistical parameters were derived from label free methods, documented as declared assumptions with sensitivity ranges
  • Every design decision, correction, and measured tradeoff logged in a running decision record (26+ entries)

What I did

  • Made every design and threshold decision: dataset selection, blocking rule design and every revision along the way (including diagnosing and fixing a rule that was generating about 80% noise from a text normalization side effect), the choice to stay fully unsupervised, the matching feature set, and the title comparison method after the default tool turned out to be unsuitable
  • Reviewed, questioned, and approved or rejected each design choice along the way, requiring verification over assertion at every step. Several proposed approaches were revised or reversed after being checked against real measurements
