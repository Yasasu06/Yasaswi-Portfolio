IT Support RAG Agent

Live and fully functional

An AI assistant that answers IT support questions by retrieving and citing real enterprise incident tickets, with adaptive retry and confidence scoring.

IT support teams repeatedly resolve similar tickets without a fast way to search past resolutions. This tool lets someone describe an issue in plain language and get a grounded answer sourced directly from historical tickets — with citations, not a hallucinated guess — including a live connection to a real ServiceNow instance.

Stack

Python, Streamlit, LangGraph, ChromaDB, OpenAI GPT-4o-mini + OpenAI embeddings, Microsoft Presidio, ServiceNow REST API, pytest, GitHub Actions, Railway

Key features

  • 4-agent LangGraph pipeline: Retrieval Agent (ChromaDB semantic search) → Answer Agent (grounded generation, cites ticket IDs) → Verification Agent (independent LLM fact-check) → Triage Agent (confidence/groundedness scoring, auto-escalation)
  • Adaptive retry: broadens and reruns the query (max 2 retries) when confidence is low — visible in the UI as a "Broadened search · N retries" badge
  • Live ServiceNow REST API integration alongside 4 other ingested data sources
  • PII masking via Presidio before any data reaches the LLM
  • Session-scoped rate limiting (15 requests / 60s) and a feedback loop (Helpful/Not Helpful voting)

What I did

  • Diagnosed and resolved a live ServiceNow production outage end-to-end: isolated a 401 error via direct curl/Python REST tests, used ServiceNow's Background Script tool to inspect system properties, identified a newly-enforced Basic Auth role restriction, and fixed it
  • Documented fine-tuning as a closed architectural decision (not pursued further) after confirming OpenAI deprecated self-serve fine-tuning for new orgs — a deliberate scope decision, not a gap
  • Directed visual design iteration using Linear.app as a reference
  • Identified and specified the retry-visibility feature, surfacing an existing backend capability that was invisible to end users

Metrics

90.0% eval accuracy (18/20) · citation accuracy 1.0 · refusal correctness 1.0 · 51/51 tests passing · 750 tickets across 4 ingested sources plus a 5th live ServiceNow connection · ~10,000 lines of Python. Groundedness 0.685 and relevance 0.69.

Cloud Intelligence Platform

Live and publicly accessible

AI-powered cloud cost analyzer that parses real billing CSVs and returns personalized waste recommendations in under 60 seconds.

Startups spending $2K–$50K/month on cloud have no cheap way to understand where money is going. AWS bills have 14+ line items across multiple services and no clear signal on what's waste. This tool does what a FinOps consultant would do manually — takes the actual bill, finds the specific waste, and tells you what to cut this week.

Stack

Next.js 14, TypeScript, Tailwind CSS, Framer Motion, DM Serif Display, Supabase (PostgreSQL + Auth + RLS), Groq API (Llama 3.3 70B) via secure backend proxy, Recharts, Stripe (test mode), PostHog, AWS Pricing API, Azure Pricing API, Vercel, GitHub Actions

Key features

  • Parses real billing CSVs from AWS, Azure, GCP, DigitalOcean, and Oracle — auto-detects provider with confidence score, shows rows parsed, services found, cost column detected
  • Groq AI generates personalized recommendations with specific dollar savings based on actual bill data — not industry averages
  • Bill history with memory — anonymous users get localStorage persistence, authenticated users get Supabase storage with month-over-month trend comparison
  • Compliance checker — pick industry and cloud provider, get instant framework requirements (HIPAA, SOC2, etc.) with specific services and cost estimates
  • Live pricing explorer — compares 12 providers in real time using AWS and Azure APIs plus verified static data for remaining providers

What I did

  • Caught that the Groq API key was exposed in the browser bundle — moved all 9 Groq call sites to a single secure backend proxy route
  • Decided to cut 48 pages down to 3 focused tools based on which ones delivered a complete real-data experience
  • Wrote the full Supabase schema from scratch — 7 tables, RLS policies, handle_new_user trigger, anonymous-to-authenticated migration
  • Chose an editorial white design (DM Serif, no gradients) deliberately to differentiate from the generic dark-mode AI project look

Metrics

Sample bill tested — 14 line items, 7 services, $2,617.57 total, parsed in under 5 seconds. Parser handles 6 billing formats (AWS CUR, AWS Cost Explorer wide-matrix, Azure Cost Management, GCP billing CSV, DigitalOcean, Oracle CUR). No production metrics yet — no real users yet.

Entity Resolution Pipeline (Walmart–Amazon)

In Progress

A blocking-and-matching system that identifies when product listings from two independent retailers describe the same real-world item, without ever using labeled training data.

Retailers routinely hold multiple records for the same product across different data sources, with no shared ID and inconsistent formatting. Naively comparing every record pair is computationally infeasible at scale. This project narrows an infeasible comparison space down to a manageable, high-recall candidate set, then scores those candidates on multiple pieces of evidence — all without access to ground-truth labels during development.

Stack

Python, DuckDB, Splink (probabilistic record linkage), Git/GitHub, pytest. Dataset: "Dirty Walmart-Amazon" entity-matching benchmark (Amazon: 22,074 records; Walmart: 2,554 records).

Key features

  • Custom blocking layer (five rules): rare-token matching, identifier-pattern detection, brand-vocabulary harvesting, character n-gram matching, symmetric nearest-neighbor fallback — reduced 56.4 million possible pairs to ~564,000 candidates (99.1% reduction) with 100% record coverage on both source tables
  • Cross-field evidence extraction from full record text (rather than trusting original field structure, which is unreliable due to data corruption) — recovered usable identifier/brand evidence for 72–99% of records vs. 16–25% using original fields directly
  • Custom word-level title similarity comparison, built after verifying Splink's built-in "Jaccard" comparison operates on characters rather than words and isn't discriminative on ~100-character product titles
  • Strict data-governance policy: no labeled data read at any point during design, tuning, or threshold-setting — only at a single final evaluation. All required statistical parameters derived from label-free methods, documented as declared assumptions with sensitivity ranges
  • Every design decision, correction, and measured trade-off logged in a running decision record (26+ entries)

What I did

  • Made every design and threshold decision: dataset selection, blocking rule design and every revision (including diagnosing and fixing a rule generating ~80% noise from a text-normalization side effect), the choice to stay fully unsupervised, the matching feature set, and the title-comparison method after the default tool was found unsuitable
  • Code implementation was AI-assisted under my direction; I reviewed, questioned, and approved or rejected each design choice, requiring verification over assertion at every step — several proposed approaches were revised or reversed after being checked against real measurements

Metrics

Blocking stage — 564,450 candidate pairs from 56,376,996 possible (99.1% reduction), 100% coverage on both source tables. Matching accuracy/precision/recall not yet measured — the matcher has just been built and is about to run for the first time.
